# Slice Header и VUI-тайминг: что читает h264-cut и зачем

Конспект по материалам спецификации H.264 (ITU-T H.264 / ISO/IEC 14496-10),
раздел 7.3.3 (*Slice layer segment syntax*) и раздел 7.4.3 (VUI).
Описывает, какие поля заголовка среза разбирает `h264-cut`
(`source/common/params.c`, `source/common/index.c`) и как они используются
для построения индекса кадра и вырезки диапазона без перекодирования.

## Заголовок среза (slice header, спека 7.3.3)
Каждый NAL-юнит типов 1–5 начинается с заголовка среза. Чтобы понять,
"где чей кадр", утилите нужны далеко не все его поля — только несколько
первых, идущих подряд в порядке синтаксиса:

* **first_mb_in_slice**: номер первого макроблока среза в кадре.
  + Главный признак границы кадра: срез с `first_mb_in_slice == 0` всегда
    начинает новый кадр (спека запрещает размещать нулевой макроблок не в
    начале кадра).
  + Если же `first_mb_in_slice > 0` и остальные опознавательные поля
    совпадают с текущим кадром — это продолжение текущего кадра
    (мульти-слайсовый поток: несколько NAL на один кадр).
* **slice_type**: тип среза — P(0), B(1), I(2), SP(3), SI(4); значения
  5–9 означают то же самое ("all slices of the picture have the same type").
  Колонка `type` в `--list` получается как `slice_type % 5`.
* **pic_parameter_set_id**: какой PPS действует для среза. Без PPS нельзя
  узнать `seq_parameter_set_id`, а без SPS — длину поля `frame_num` и тип
  POC, то есть дальше заголовок вообще не распарсить. Смена `pps_id` —
  признак нового кадра.
* **frame_num**: счётник кадров в порядке декодирования внутри
  последовательности (ширина поля — `log2_max_frame_num` из SPS).
  + Участвует в группировке срезов в кадр: `frame_num` у всех срезов одного
    кадра одинаков; изменение — новый кадр.
  + Используется для POC при `pic_order_cnt_type == 2` (см. ниже).
* **field_pic_flag / bottom_field_flag** (только если `frame_mbs_only_flag == 0`):
  кадры-поля чересстрочного контента; их смена тоже разрезает кадр.
  Поддержка чересстрочности в утилите частичная.
* **idr_pic_id**: присутствует только в IDR-срезах (NAL type 5).
  + Нужен для группировки: IDR-срез с тем же `idr_pic_id`, что и
    предыдущий IDR-срез, принадлежит тому же кадру (типично для
    мульти-слайсовых IDR). Смена `idr_pic_id` — новый IDR-кадр.
* **pic_order_cnt_lsb** (при `pic_order_cnt_type == 0`): "младшая часть"
  номера кадра в порядке *отображения*, ширина — `log2_max_pic_order_cnt_lsb`
  из SPS. Источник POC (см. ниже).

### Важно: frame_num читается и для IDR-срезов
Согласно тексту поздних редакций спеки (7.3.3), `frame_num` и флаги полей
должны присутствовать в заголовке только **не-IDR** срезов
(`if ( !nal_unit_type == 5 ) { frame_num ... }`). Однако фактически
кодеры пишут это поле и в IDR-срезах:

* x264 в `slice_header_write()` пишет `frame_num` безусловно;
* FFmpeg в `decode_slice_header()` читает `frame_num` безусловно;
* h264bitstream (`read_slice_header`) делает то же самое.

Если читать `frame_num` только для не-IDR (буквально по спеке), то на
потоках x264 остаток IDR-заголовка будет прочитан со смещением и кадр
окастся нераспарсенным. Поэтому `h264-cut` читает `frame_num` (и флаги
полей) для всех типов срезов — как x264, FFmpeg и h264bitstream.

## PicOrderCnt (POC) — порядок отображения
Порядок декодирования ≠ порядку отображения: B-кадры декодируются позже
кадров, которые идут раньше по времени показа. Пример GOP из `--list` для
`-g 15 -bf 2`:

```
порядок декодирования: I P B B P B B ...
порядок отображения:   I B B P B B P ...
```

`PicOrderCnt` — monotонный номер кадра в порядке отображения
(спека 8.2.1). `h264-cut` считает его, чтобы сопоставить `dec_id` и
`disp_id` в `--list` и чтобы `--exact` мог переводить время в номера
кадров.

### Тип 0 (pic_order_cnt_type == 0)
В потоке передаётся только `pic_order_cnt_lsb` — младшие
`log2_max_poc_lsb` битов; старшая часть (`pic_order_cnt_msb`) восстанавливается
декодером из предыдущего значения. Буквальная формула спеки сравнивает
`pic_order_cnt_lsb` с удвоенным предыдущим значением и опирается на
`offset_for_non_ref_pic`, что на реальных потоках легко ломает монотонность.
`h264-cut` использует реализацию FFmpeg (`ff_h264_init_poc`) — эквивалентную
на корректных потоках, но устойчивую к переполнению:

```
max_lsb = 1 << log2_max_pic_order_cnt_lsb
msb = prev_msb + max_lsb,  если lsb < prev_lsb  и prev_lsb - lsb >= max_lsb / 2   (перехлёст вверх)
msb = prev_msb - max_lsb,  если lsb > prev_lsb  и lsb - prev_lsb >  max_lsb / 2   (перехлёст вниз)
msb = prev_msb иначе
poc   = msb + lsb
```

Ключевой "half-range guard": сдвиг старшей части происходит только тогда,
когда разница `lsb` составляет половину и более диапазона. Без этого
защитного условия нормальный ход POC в GOP с B-кадрами (6, 2, 4, 12, 8, ...)
в порядке декодирования выглядел бы как "перехлёст", и монотонность терялась
бы уже внутри первого GOP. Для IDR: `poc = 0`, состояние сбрасывается.

### Тип 2 (pic_order_cnt_type == 2)
POC не передаётся вовсе, порядок отображения выводится из `frame_num`:

```
PicOrderCnt = 2 * FrameNumOffset - (nal_ref_idc == 0 ? 1 : 0)
```

где `FrameNumOffset` — "развёрнутое" значение `frame_num` (при каждом
перехлёсте модульного счётчика добавляется `max_frame_num`, при IDR обнуляется).
B-кадры (unreferenced, `nal_ref_idc == 0`) получают нечётные значения и
корректно встают между ссылочными кадрами.

### Тип 1
Не поддерживается: порядок отображения полей/кадров зависит от
`offset_for_ref_frame` и дельт для полей, которые в общем случае не
восстанавливаются без полного декодирования. При встрече SPS с
`pic_order_cnt_type == 1` у всего потока обнуляется `display_index`
(в `--list` это `-`), а `--exact` завершается с кодом `2`.

## VUI: timing_info — откуда берётся fps
В расширенной части SPS могут присутствовать VUI-параметры
(`vui_parameters_present_flag`), и в них — блок `timing_info`:

* **num_units_in_tick**, **time_scale**: длительность одного "тика" равна
  `num_units_in_tick / time_scale` секунд; кадр занимает два тика, поэтому

```
fps = time_scale / (2 * num_units_in_tick)
```

  Например, 25 fps: `time_scale = 50`, `num_units_in_tick = 1`.
* **fixed_frame_rate_flag**: `1` — поток с постоянным числом кадров
  (без повторов/пропусков), т.е. время n-го кадра отображения ровно
  `n / fps`. Это то предположение, на котором работает `--exact`.

`h264-cut` берёт тайминг из первого распознанного SPS; флаг
`--fps` имеет приоритет над VUI (VUI может отсутствовать или быть
некорректным).

## Как индекс относит параметрические NAL к следующему кадру
SPS, PPS, SEI, AUD и прочие "служебные" NAL-юниты стоят в потоке *перед*
кадром, к которому относятся. Индекс `h264-cut` атрибутирует их именно так:
все NAL, встреченные после последнего среза, включаются в диапазон
**следующего** начинающегося кадра (`frame.nal_first .. frame.nal_last`,
колонка `nal_range` в `--list`). В результате:

* диапазон NAL IDR-кадра самодостаточен: содержит свои SPS/PPS/AUD/SEI;
* вырезка `[IDR .. b]` — замкнутый closed-GOP, который можно вставить в
  другой поток (при необходимости актуальные SPS/PPS дописываются
  утилитой, если в AU первого кадра их нет).

## Почему вырезка начинается с IDR, а правую границу двигать не надо
Левая граница всегда сдвигается назад к ближайшему IDR-кадру
(с предупреждением в stderr). Причина:

* P/B-кадры предсказываются из других кадров, и по порядку **декодирования**
  любой кадр ссылается только на кадры, лежащие строго *раньше* него.
* Если отрезать поток посередине GOP, первые кадры вырезки будут ссылаться
  на отсутствующие опорные кадры — результат недесибелен корректно.
* IDR сбрасывает все опорные списки (и обнуляет `frame_num`/POC), поэтому
  сегмент `[IDR .. b]` самодостаточен: **ничего из хвоста не нужно**.

Отсюда же следует, что правую границу расширять не требуется: кадры после
`b` на кадры из `[IDR .. b]` не влияют (влияние возможно только назад по
декодерному порядку). Хвостовые B-кадры, которые по времени отображения
опережают последний сохранённый кадр, просто остаются за вырезкой.

## Нормализация start code при записи
Annex B допускает старт-коды длиной 3 байта (`00 00 01`) и 4 байта
(`00 00 00 01`, где лидирующий ноль — `zero_byte`), а также хвостовые
байты заполнения `trailing_zero_8bits` между NAL. При разборе потока
индекс сохраняет только полезную нагрузку NAL (байты после старт-кода,
без хвостовых нулей). Поэтому при записи вырезки:

* перед каждым NAL пишется канонический **4-байтный** старт-код
  `00 00 00 01` (валиден для любого NAL, `zero_byte` разрешён всегда);
* хвостовые нули между NAL исходника отбрасываются (это заполнение, не данные);
* сами байты NAL копируются **байт-в-байт**, включая байты
  `emulation_prevention_three_byte` — перекодирования/перемаркировки нет.

Именно эту инвариантность ("полезная нагрузка NAL не меняется") проверяет
интеграционный тест `tests/run.sh` (T3/T4) вместе с `tests/nal_seq.py`.
